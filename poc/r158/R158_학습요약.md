## 2. R158 판정 기준 (킥오프 / 코드)

T0 = R단 변속(후진 이벤트 시작, 보통 CAN 또는 기어/클러스터 R 검출).

| # | 조건 | 의미 |
|---|------|------|
| ① | 팝업 일치 | 클러스터 경고 화면이 기대 템플릿과 일치 |
| ② | 경고음 일치 | 기대 경고음(파형·주파수) onset 검출 |
| ③ | 응답시간 ≤ 0.6s | 팝업·경고음·경고CAN **각각**이 T0 + 0.6초 이내 |
| ④ | 동기 오차 ≤ 30ms | 팝업·경고음·경고CAN onset의 `max−min ≤ 30ms` |

전체 PASS = ①~④ 모두 만족.

### 2.1 동기 30ms vs 응답 0.6s

- **0.6s**: T0 대비 “너무 늦게 뜨면 안 됨”
- **30ms**: 서로 “파파박” 같이 뜨는지 (상호 간격)
- 예: 경고음 420ms, 클러스터 430ms, CAN 440ms → 응답 OK, 동기 20ms OK
- 예: 경고음 100ms, 클러스터 500ms → 응답은 OK여도 동기 400ms FAIL

### 2.2 문서의 30ms가 “판단 속도”인가?

- **아님.** 킥오프에 “판단 속도 ≤ 30ms” 명시 조항 없음.
- 문서 30ms =
  1. UX 상호 동기 오차
  2. p9 C5: 웹캠 영상–음성 Sync ≤ 30ms
- “판단도 빨라야 한다”는 **30ms 동기를 왜곡 없이 측정하기 위한 도구 성능 함의**.

### 2.3 동기 검증의 본질

- 목표가 “측정 시각끼리의 숫자 맞추기”가 아님.
- **실차에서 실제로** 팝업·음향·CAN이 30ms 안에 같이 발생했는지 **검출·판정**하는 것.
- 실차가 진짜 70ms 어긋나면 FAIL이 정상.
- 도구 채널별 분석/캡처 지연이 들쭉날쭉하면 **가짜 동기 오차**가 생김  
  (예: 영상 +70ms, 음향 +30ms → 실제 동시인데 40ms FAIL처럼 보임).
- 따라서 채널 분석은 수 ms대, 스탬프는 가능하면 도착/샘플 시각 기준으로 통일.

## 3. 시험 모드 vs 문서/법규 모드

### 3.1 현재 방향: 시험 모드

- 30fps로 테스트 가능.
- 동기 허용치를 UI에서 설정 (예: 40ms) → `max−min ≤ 설정값`이면 동기 PASS.
- R단 이동 시 팝업·음향·CAN을 **병렬 검출**, 동기화가 설정값 이내면 PASS.
- 시험 모드에서는 허용치 완화(40ms 등) OK.

### 3.2 문서/법규 모드 (향후)

- 동기 기본/고정 **30ms**
- 응답 **0.6s**
- 기대값 일치(팝업·음향) 포함
- 전체 PASS = ①~④

## 4. 기대 음향 검증 표현 (BeepMatcher)

### 4.1 기대값 본체

- 주 기준: 기대 경고음 `.wav` 템플릿 (`expected/warning_*.wav` 등)
- 보조 메타: `expected/expected.json`의 `beep_freq`, `sr` 등
- 내부: 긴 경고음에서 에너지 최대 “삐 한 번” 단일 펄스 추출 → 단위정규화

### 4.2 두 지표

| 지표 | 방법 | 의미 |
|------|------|------|
| `waveSim` | 시간영역 NCC(정합필터) | 삐 한 번의 **파형 모양** |
| `freqSim` | FFT 크기 스펙트럼 코사인 유사도 | **스펙트럼 모양 전체** (peak Hz 하나만 아님) |

- 판정: `(freqSim ≥ freqThr) AND (waveSim ≥ waveThr)` → PASS
- `targetFreq`는 대역 에너지 트리거용 peak; `freqSim` 계산의 전부가 아님
- 직관: 파형 = 소리 실루엣, 주파수 = 음높이가 센 분포(스펙트럼 형태)

## 5. 영상 판정 (RoiMatchDetector)

- ORB로 프레임을 canon **640×640** 좌표계로 정렬 후, 고정 ROI만 NCC로 비교 (SSIM은 참고, 게이트는 NCC).
- `passMs ≈ frameGapMs + analysisMs`
- 입력 해상도(720/1080)와 무관하게 판정은 640에서 수행 → PASS **속도**만 보면 고해상도 이점 거의 없음.
- 같은 30fps면 720p가 1080p보다 미세하게 유리(전송·resize 부담).
- 현재 sarxos(YUY2)는 720p+에서 USB 대역으로 **15fps로 떨어지기 쉬움** → 앱은 640급으로 **30fps 유지**가 속도에 유리.
- Logitech **C930e는 최대 30fps** (1080p/720p 모두). 설정으로 60fps 불가. 60fps는 Brio 등 다른 기종.

## 6. USB 카메라 프레임 간격

- “30fps ≈ 33.3ms”는 **평균/공칭**이지 **하한/고정 주기**가 아님.
- USB·드라이버 지터로 순간 간격 26·31·35ms 등은 **정상**.
- 이상 징후는 순간 최소값보다 **장기 평균이 ~66ms(15fps)** 로 굳는지.

## 7. 폴링 / 중복 스킵 / 판단 속도

### 7.1 목적

- 30ms 동기를 재려면 도구 시간 분해능·검출 지연이 그보다 충분히 짧아야 함.
- 30fps(≈33ms)만으로는 한 프레임이 이미 기준과 비슷해 “파파박” 측정이 불리.

### 7.2 설계 방향

- **이전**: 폴링을 길게(예: 60ms) → CPU↓ but 폴링 양자화 지연↑
- **목표**: 폴링을 짧게(예: 4ms) + **같은 프레임 중복 스킵** → CPU는 프레임당 1회, 새 프레임은 바로 잡음
- 폴링을 줄인다고 `analysisMs` 자체가 줄어드는 게 아니라, **늦장 폴링 대기**를 제거하는 것.

### 7.3 코드 주의

- `GearView`/`ClusterView` `POLL_MS` 등은 변경될 수 있음.
- `frameSig`로 gap은 “새 프레임”만 재지만, **조기 return(진짜 중복 스킵)** 이 없으면 짧은 폴링만으로 CPU가 폭주할 수 있음.
- 올바른 조합: 짧은 폴링 + sig 동일 시 판정/UI 스킵 + sig 변경 시에만 전체 판정.

### 7.4 Sarxos

- 발음: **사르크소스** (SAR-ksoss). webcam-capture 라이브러리 저자 닉네임.

## 8. 에이전트가 지켜야 할 결론 문장

1. 동기 30ms = **실차 UX 상호 발생 간격** 검증 목표이지, “판단 속도 법규 항목”이 아니다.
2. 도구가 빨라야 하는 이유 = 그 실제 동기를 **가짜 지연 없이 측정**하기 위해서다.
3. 시험 모드 = 동기 허용치 설정 가능(예: 40ms), 30fps 테스트 OK.
4. 문서 모드 = 30ms + 0.6s + 기대값 일치.
5. 음향 = wav 템플릿 + wave(NCC) AND freq(스펙트럼 코사인).
6. 영상 = canon 640 + NCC; C930e는 30fps 상한.
7. 프레임 gap < 33ms 순간값은 USB 지터로 정상일 수 있다.
