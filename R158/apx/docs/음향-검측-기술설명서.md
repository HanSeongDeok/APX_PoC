마이크로 들어온 소리를 짧은 조각으로 끊어 받고, 조각마다 "기대 경고음과 같은 소리인가"를 **주파수**와 **파형** 두 각도로 점수 내어, 두 점수가 모두 기준선을 넘은 첫 순간을 기록한다.

비전이 지표 하나(NCC)만 쓰는 것과 달리 **음향은 두 지표를 AND로 묶습니다.** 이유는 3장에 있습니다.

## 1. 마이크 연결과 입력 레벨

### 데모에서 보는 것

설정 화면 마이크 그룹에 선택 콤보와 **입력 레벨 막대**, **마이크 테스트** 버튼이 있습니다. 테스트를 켜고 말하면 막대가 움직입니다.

### 소리를 어떻게 받는가

Java 표준 오디오(`javax.sound.sampled`)로 받습니다. 별도 드라이버를 설치하지 않습니다.

| 항목 | 값 |
|---|---|
| 형식 | 16bit, 모노, little-endian |
| 표본율 | 기대 경고음 `.wav`의 표본율을 그대로 따름 (데모 48kHz) |
| 한 조각 크기 | **2048 표본** |
| 조각 주기 | 2048 / 48000 = **42.7ms** |

**조각 주기가 이 채널의 시간 분해능을 결정합니다.** 8장에서 다시 다룹니다.

### 입력 레벨 막대를 먼저 보는 이유

파형이 평평하거나 판정이 안 붙을 때, **레벨을 먼저 확인하는 것이 가장 빠릅니다.**

레벨은 세 곳에서 각각 깎입니다.

```
스피커 출력 볼륨  →  공기  →  마이크 입력 볼륨  →  Windows 통신 자동 볼륨 조정
```

실제로 겪은 사례입니다. 재생 20% × 입력 29%로 곱해져 피크 진폭이 **0.0017**까지 떨어졌습니다. 파형 그래프의 Y축은 ±100% 고정이라 화면상 완전히 평평했고, 판정 점수도 무너졌습니다. 재생 70% / 입력 100%로 올리자 진폭 **0.1782**(105배), 주파수 일치도가 0.895 → **0.996** 으로 올랐습니다.

**레벨이 낮으면 점수도 같이 무너집니다.** 임계를 내리기 전에 레벨을 보십시오.

> Windows **통신 자동 볼륨 조정**은 기본값이 "다른 소리 80% 줄이기"입니다. 측정은 마이크를 여는 행위이므로 Windows가 이를 통화로 보고 기대음을 깎을 수 있습니다. 제어판 → 소리 → 통신 탭에서 **"아무 작업도 하지 않음"** 으로 두는 것을 권장합니다.

### 마이크 선택 시 주의

**에코 캔슬링 스피커폰의 마이크를 쓰지 마십시오.**

스피커폰은 자기 스피커가 낸 소리를 자기 마이크에서 능동적으로 제거합니다. 그게 그 장치의 존재 이유입니다. 그런데 우리가 검출해야 하는 신호가 정확히 그 제거 대상입니다.

실측 비교입니다. 같은 소리, 같은 조건입니다.

| 마이크 | 피크 진폭 | 주파수 일치도 | 파형 일치도 |
|---|---|---|---|
| 일반 웹캠 마이크 | 0.056 | **0.988** | **0.950** |
| 에코 캔슬링 스피커폰 | 0.005 | 0.675 | 0.542 |

진폭이 10배 이상 깎이고 일치도는 임계 근처에도 못 갑니다. 입력 볼륨을 100%로 올려도 개선되지 않습니다. 게인이 아니라 신호를 빼는 처리이기 때문입니다.

**스피커는 스피커폰으로, 마이크는 별개 장치로** 나누는 것이 정답입니다.

## 2. 기대 경고음 등록

### 데모에서 보는 것

`.wav` 파일을 고르고, **기대음 재생** 버튼으로 스피커에서 들어봅니다.

### 파일 전체를 비교하지 않습니다

경고음은 보통 "삐 — 삐 — 삐" 처럼 같은 소리가 반복됩니다. 파일 전체를 비교 대상으로 삼으면 문제가 생깁니다.

- 마이크로는 **몇 번째 삐**가 들어올지 알 수 없습니다
- 반복 주기가 차종마다 다릅니다
- 전체를 기다리면 검출이 그만큼 늦습니다

그래서 등록한 파일에서 **에너지가 가장 센 짧은 구간 하나**만 잘라 씁니다. 삐 한 번입니다.

```java
int plen = min(전체길이, max(10ms, pulseSec * sr));   // pulseSec = 0.015 → 15ms
// 슬라이딩 창의 에너지 합이 최대인 위치를 prefix-sum 으로 찾아 잘라낸다
pulse = Arrays.copyOfRange(t, best, best + plen);
this.tmpl = SignalMath.unitNormalize(pulse);
```

**펄스 한 번을 정합필터(matched filter)로 쓰는 방식**입니다. 반복 주기가 달라도 각 펄스의 모양은 같으므로, 몇 번째 삐가 들어오든 같은 점수가 나옵니다.

### 목표 주파수는 자동으로 뽑습니다

잘라낸 펄스에 창함수(Hanning)를 씌우고 FFT를 걸어, **에너지가 가장 큰 주파수**를 목표 주파수로 잡습니다.

```java
this.targetFreq = argmax(spec) * sr / specN;
```

사람이 "몇 Hz입니다" 하고 입력하지 않습니다. 파일에서 읽어냅니다. 화면에는 이 값이 `목표 주파수 656 Hz` 처럼 표시됩니다.

### 되돌아보는 창은 0.5초입니다

```java
this.buflen = Math.max(l, (int) (0.5 * sr));   // 0.5초 롤링 버퍼
```

조각이 들어오면 이 버퍼를 밀어 넣고, **최근 0.5초**를 놓고 판정합니다. 조각 하나(42.7ms)만 보면 펄스가 조각 경계에 걸려 잘릴 수 있어서, 겹치는 창을 두는 것입니다.

## 3. 판정 원리

### 데모에서 보는 것

측정을 켜면 파형 그래프가 흐르고, 아래에 두 줄이 갱신됩니다.

```
주파수 일치도  0.99  ≥ 임계 0.90  충족
파형 일치도    0.95  ≥ 임계 0.90  충족
```

### 두 지표를 AND로 묶습니다

```java
boolean isPass = (freqSim >= freqThr) && (waveSim >= waveThr);
```

비전은 지표 하나(NCC)만 쓰는데 음향은 둘을 씁니다. 두 지표가 서로 다른 실패를 잡기 때문입니다.

| 지표 | 무엇을 보나 | 이것만 쓰면 |
|---|---|---|
| **주파수 일치도** | 소리의 음색 (어느 주파수에 에너지가 있나) | 음높이만 같은 다른 소리에 속습니다 (예: 다른 기기의 비프) |
| **파형 일치도** | 소리의 모양 (시간축에서 어떻게 오르내리나) | 비슷한 모양의 잡음(문 닫힘, 노크)에 속습니다 |

둘을 함께 요구하면 **"같은 음색이면서 같은 모양"** 이어야 통과합니다. 실차 실내는 잡음이 많은 환경이라 이 조건이 필요합니다.

### 주파수 일치도 — 스펙트럼 코사인 유사도

최근 구간에 창함수를 씌우고 FFT를 걸어 크기 스펙트럼을 구한 뒤, 기대 펄스의 스펙트럼과 **방향이 얼마나 같은지**를 봅니다.

```java
double[] mag = Fft.magnitude(SignalMath.mul(seg, SignalMath.hanning(l)));
// 두 스펙트럼을 각각 단위벡터로 만든 뒤 내적 = 코사인 유사도
double v = SignalMath.dot(sn, tmplSpec);
return clamp(v, 0, 1);
```

두 벡터를 **단위벡터로 정규화한 뒤 내적**하므로, 소리가 크든 작든 값이 변하지 않습니다. 스펙트럼의 "모양"만 봅니다. 밝기에 무관한 비전의 NCC와 같은 발상입니다.

### 파형 일치도 — 정규화 상호상관 최대값

기대 펄스를 최근 0.5초 위로 **미끄러뜨리며** 각 위치의 닮은 정도를 계산하고, 그 최대값을 씁니다.

```java
double waveSim() {
    double[] seg = 최근 0.5초;
    return SignalMath.nccMax(seg, tmpl);
}
```

미끄러뜨리는 이유는 **펄스가 구간 안 어디에 있을지 모르기 때문**입니다. 위치를 찾아가며 비교합니다.

계산 방식에 두 가지 장치가 있습니다.

- **분자(상관값)는 FFT로** 구합니다. 합성곱 정리를 쓰면 O(S·logS)로, 직접 계산(O(S·L))보다 훨씬 빠릅니다. 실시간 처리에 필요합니다
- **분모(구간 에너지)는 누적합으로** 구합니다. 각 위치의 에너지를 O(1)에 얻습니다
- **무음 구간은 제외**합니다. 최대 에너지의 10% 미만인 위치는 후보에서 빼서, 조용한 구간에서 잡음이 우연히 높은 점수를 내는 것을 막습니다

### 소리 유무는 별도로 봅니다

목표 주파수 ±150Hz 대역의 에너지를 **배경 소음과 비교**합니다.

```java
double e = bandEnergy(block);              // 목표 주파수 근처 대역 에너지
bg = (bg == null) ? e : 0.98*bg + 0.02*e;  // 배경 에너지 이동평균
double ratio = e / max(bg, 1e-6);
boolean hasSound = ratio >= 4.0;           // 배경의 4배 이상이면 "소리 있음"
```

배경을 **이동평균으로 계속 갱신**하므로, 실내 소음이 큰 곳에서도 기준이 그 환경에 맞춰집니다.

화면에는 `에너지비 35.9배 · 소리 있음` 처럼 표시됩니다.

### 소리 유무는 판정 조건에 넣지 않습니다

중요한 설계 결정입니다. 코드 주석에 이유가 적혀 있습니다.

```java
// 확정 = 주파수 AND 파형 일치(isPass). 에너지 급증(hasSound)은 게이트에서 제외:
//   콜드스타트(소리 먼저 재생 후 측정 시작)엔 배경 대비 급증이 없어 hasSound가
//   안 뜬다. 에너지 온셋은 항상 있다고 가정하고, 강한 조건인 isPass로만 확정.
```

경고음이 **이미 울리고 있는 상태에서 측정을 시작**하면, 그 소리가 배경으로 학습되어 "급증"이 없습니다. 그때 `hasSound`를 필수로 걸면 영원히 검출되지 않습니다. 그래서 소리 유무는 **참고 표시**로만 쓰고, 판정은 더 강한 조건인 두 일치도로만 합니다.

## 4. 기준선 정하기

### 데모에서 보는 것

임계 버튼으로 값을 올리고 내립니다. **주파수와 파형은 하나의 값을 공유**합니다.

```
PASS 기준 임계   0.90
[− 완화]  [+ 엄격]
```

기본값 **0.90**, 조정 단위 0.05입니다.

### 하나의 값을 쓰는 이유

두 지표에 다른 값을 주면 "왜 주파수는 0.85고 파형은 0.92인가"를 설명해야 합니다. 근거를 만들기 어렵고 조합이 늘어납니다. 하나로 묶으면 **"일치도 90% 이상"** 이라는 한 문장으로 설명됩니다.

### 정하는 절차

1. **레벨을 먼저 맞춥니다** — 1장. 레벨이 낮으면 점수가 무너져서 임계를 잘못 정합니다
2. 기대음을 재생해 **두 일치도를 봅니다** — 실측 예: 0.996 / 0.962
3. 조용한 상태에서 **잡음만 있을 때 값을 봅니다** — 보통 0.3 이하
4. 두 값 사이에 둡니다. 실측 기준 **0.90이면 충분한 여유**가 있습니다

정상 값이 0.90에 못 미치면 임계를 내리기 전에 **레벨과 마이크 선택을 먼저 점검**하십시오. 실측에서 그 두 가지로 0.895 → 0.996 까지 올라갔습니다.

### 기대음 선택도 점수에 영향을 줍니다

같은 조건에서 파일만 바꿔 잰 값입니다.

| 기대음 | 주파수 일치도 | 파형 일치도 | 임계 0.90 |
|---|---|---|---|
| `PDW_Rear_1.wav` | **0.996** | **0.962** | 통과 |
| `Gear_R.wav` | 0.895 | 0.902 | 탈락 |

펄스가 뚜렷하게 분리된 소리가 유리합니다. 여러 파일이 있으면 **설정 화면에서 비교해 고르십시오.**

## 5. 발사와 검출 (슬레이트)

### 데모에서 보는 것

시뮬레이션 시작 후 기어봉을 P에서 R로 바꿉니다. 그러면 도구가 기어봉 화면에서 R을 **검출한 순간**에 기대 경고음이 스피커로 나갑니다.

### 왜 검출 순간에 발사하는가

영화 슬레이트와 같은 구조입니다.

```
Ready    기어봉 화면 P → R                      (버튼)
Action   도구가 기어봉 ROI PASS 검출  = T(0)     ← 슬레이트가 "탁"
         ├→ 클러스터 R 팝업 화면 교체
         └→ 기대 경고음 발사
Sync     MAX(클러스터 검출 − T0,  음향 검출 − T0)
```

버튼을 누른 순간이 아니라 **검출된 순간**에 발사하는 것이 핵심입니다. 그래야 **T(0)를 도구가 정확히 압니다.** 그 뒤 소리를 다시 마이크로 받기까지의 시간이 곧 **음향 채널의 파이프라인 지연**이고, 클러스터 쪽 지연과 비교하면 **두 채널의 동기 오차**가 나옵니다.

### 발사 지연을 미리 없앱니다

측정 시작 시 오디오 라인을 **미리 열어 둡니다.**

```java
expectedPlayer.prepare(wav.samples, wav.sampleRate);   // start() 에서
```

준비 없이 발사하면 그 순간 라인을 여느라 수십 ms가 걸리고, **그 지연이 그대로 음향 지연에 얹혀** 측정값을 오염시킵니다. 미리 열어 두면 발사는 버퍼에 쓰기만 하면 됩니다.

### 한 측정에 한 번입니다

기어봉 PASS와 기대음 발사 모두 **측정당 1회로 잠깁니다**(래치). 다시 하려면 측정을 중지하고 다시 시작합니다.

동기 오차는 회차마다 값이 다르므로(8장) **1회로는 판단할 수 없습니다.** N회 반복해 중앙값과 편차를 보아야 합니다.

## 6. PASS/FAIL 판정 시점

### 데모에서 보는 것

경고음이 검출되면 이 줄이 뜨고 **그 뒤로 바뀌지 않습니다.**

```
음향: PASS @ 1268 ms (자체판단 48.5 = 간격 42.7 + 분석 5.8)
```

파형 그래프에는 PASS 구간이 **초록 밴드**로 칠해집니다.

### 판정 규칙

```java
if (armed && Double.isNaN(onsetT) && isPass) {
    onsetT = now;                                  // 처음 넘은 순간으로 고정
    match = true;
    double analysisMs = (System.nanoTime() - tAna0) / 1e6;
    pass = new double[] { blockGapMs + analysisMs, blockGapMs, analysisMs };
}
```

비전과 같은 **래치**입니다. 점수는 계속 오르내리지만 PASS 시각은 **처음 넘은 그 순간 하나로 고정**됩니다. 법규가 재는 것이 "경고가 처음 난 시점"이기 때문입니다.

### 표시 숫자 읽는 법

| 항목 | 의미 |
|---|---|
| PASS @ 1268 ms | 측정 시작을 0으로 한 검출 시각 |
| **간격 42.7** | 오디오 조각 주기(2048 / 48000). 소리가 조각 중간에 시작하면 그 조각이 다 차기를 기다려야 알 수 있습니다 |
| 분석 5.8 | FFT와 상관 계산에 든 시간 |
| 자체판단 48.5 | 위 둘의 합. 도구가 만든 지연 |

비전의 "간격"이 카메라 프레임 주기인 것과 같은 자리입니다. **음향은 42.7ms로 비전(33.3ms)보다 큽니다.** 8장의 핵심입니다.

## 7. 남기는 증거

### 데모에서 보는 것

중지 후 지정한 폴더의 `audio/` 아래에 있습니다.

| 파일 | 내용 |
|---|---|
| `full.wav` | 측정 전 구간 녹음 |
| `clip.wav` | **PASS 시작부터 PASS 해제까지** 잘라낸 구간 |
| `wave_pass.png` | PASS 시점 주변 파형 그래프 |
| `wave_full.png` | 전 구간 파형 그래프 |

### 각각을 남기는 이유

**`full.wav`** — 판정을 나중에 다시 검증할 수 있는 원본입니다. 임계를 바꿔 재판정해 보거나, 잡음이 섞였는지 귀로 확인할 수 있습니다.

**`clip.wav`** — 보고서에 붙일 짧은 근거입니다. 전 구간 파일은 길어서 그대로 쓰기 어렵습니다. PASS로 판정된 그 소리만 들어볼 수 있습니다.

**파형 png 두 장** — 문서에 그림으로 넣을 용도입니다. `wave_pass.png`는 판정 순간을 확대해 보여주고, `wave_full.png`는 측정 내내 다른 소리가 없었는지를 보여줍니다.

클라이언트가 **임의 구간을 잘라 wav나 png로 뽑는 것**도 지원합니다. 특정 시점을 따로 근거로 써야 할 때 사용합니다.

## 8. 고객이 알아야 할 정확도 한계

이 절은 숨기지 않고 명시합니다. 30ms 논의에 직접 영향을 줍니다.

### ① 조각 주기 42.7ms가 이 채널의 시간 분해능입니다

가장 큰 오차 항목입니다.

```
2048 표본 / 48000 Hz = 42.7ms
```

| | 오차 |
|---|---|
| 최선 (소리가 조각 시작과 맞음) | 거의 0 |
| 최악 (소리가 조각 시작 직후) | 42.7ms |
| 평균 | 약 21.3ms |

**이 오차만으로 30ms 예산을 넘길 수 있습니다.** 그리고 회차마다 값이 달라서(랜덤) 보정으로 없앨 수 없습니다.

**개선 방법이 있고 아직 적용하지 않았습니다.** 상관 계산이 **조각 안 어디에서 일치했는지를 이미 알고 있는데** 최대값만 쓰고 위치를 버립니다.

```java
public static double nccMax(double[] seg, double[] tmpl)      // 최대값만 반환
public static int    bestNccLag(double[] seg, double[] tmpl)  // 위치를 주는 함수 — 이미 있음
```

`bestNccLag`로 위치를 얻어 `t_onset = t_조각끝 − (n − 위치)/sr` 로 계산하면 **표본 단위 시각**이 나옵니다. 42.7ms → 사실상 0입니다. **이 수정 없이는 30ms를 만족하기 어렵습니다.**

### ② 표시되는 PASS 시각에는 하드웨어 지연이 포함되어 있습니다

```
표시 시각 = 실제 소리 발생 시각
          + 스피커/DAC 버퍼 + 공기 전파 + 마이크/드라이버 버퍼
          + 조각 대기 + 분석 시간
```

앞의 세 항목(하드웨어 경로)은 **현재 측정하지 않으며 보정하지 않습니다.** 표시되는 값은 "우리가 알게 된 시각"입니다.

공기 전파는 계산할 수 있습니다 — 1m당 약 2.9ms입니다. 스피커와 마이크 거리를 기록해 두면 그만큼은 설명할 수 있습니다.

### ③ 비전과 비교하면 두 오차가 함께 실립니다

| 채널 | 양자화 주기 | 평균 오차 |
|---|---|---|
| 비전 (30fps) | 33.3ms | 16.7ms |
| 음향 (2048 @48kHz) | 42.7ms | 21.3ms |

두 채널 차이의 표준편차는 약 **15.6ms**입니다(두 균등분포 차이). 즉 **2σ ≈ 31ms** — 물리지연을 완벽히 보정해도 양자화만으로 약 5%가 30ms를 넘습니다.

음향 onset 보간(①)을 적용하면 음향 항이 사라져 표준편차가 **9.6ms**로 떨어집니다. 카메라를 60fps로 올리면 **4.8ms**입니다.

### ④ 레벨이 낮으면 점수 자체가 신뢰할 수 없습니다

1장의 실측이 그 사례입니다. 진폭이 100분의 1로 깎이자 주파수 일치도가 0.996에서 0.895로 떨어졌습니다. 소리가 작으면 스펙트럼과 상관 구조가 함께 무너집니다.

**임계를 내려서 대응하면 안 됩니다.** 레벨을 먼저 올려야 합니다.

## 부록 C — 자주 나올 질문

**Q. 왜 지표가 두 개입니까? 비전은 하나인데요.**

실차 실내는 잡음이 많습니다. 주파수만 보면 음높이가 비슷한 다른 기기 소리에 속고, 파형만 보면 모양이 비슷한 충격음(문 닫힘, 노크)에 속습니다. 두 조건을 함께 요구하면 **"같은 음색이면서 같은 모양"** 이어야 통과합니다.

비전은 카메라가 정해진 사각형만 보므로 잡음원이 훨씬 적어 하나로 충분합니다.

**Q. 경고음 파일 전체와 비교하지 않는 이유는?**

경고음은 반복 패턴입니다. 마이크로 몇 번째 반복이 들어올지 알 수 없고, 전체를 기다리면 검출이 늦습니다. 그래서 **에너지가 가장 센 15ms 펄스 하나**만 잘라 정합필터로 씁니다. 반복 주기가 달라도 각 펄스 모양은 같습니다.

**Q. 목표 주파수를 직접 입력해야 합니까?**

아닙니다. 등록한 파일의 펄스에 FFT를 걸어 **가장 센 주파수를 자동으로** 뽑습니다. 화면에 표시되므로 값이 타당한지 눈으로 확인만 하시면 됩니다.

**Q. 조용한 곳에서만 되는 것 아닙니까?**

배경 소음을 **이동평균으로 계속 갱신**하므로 기준이 그 환경에 맞춰집니다. 다만 소음이 크면 신호 대비 잡음이 나빠져 일치도가 떨어집니다. 마이크를 스피커에 가까이 두는 것이 가장 확실한 대응입니다.

**Q. 경고음이 이미 울리는 상태에서 측정을 시작해도 잡힙니까?**

잡힙니다. 그 경우를 위해 **소리 유무(에너지 급증)를 판정 조건에서 뺐습니다.** 이미 울리는 소리는 배경으로 학습되어 급증이 없기 때문입니다. 판정은 두 일치도만으로 합니다.

**Q. 같은 시험을 다시 돌리면 같은 시각이 나옵니까?**

계산은 같은 결과를 냅니다. 다만 **PASS 시각은 조각 타이밍 때문에 매번 최대 42.7ms 다릅니다**(8장 ①). 그래서 한 번 재고 판단하면 안 되고 여러 번 반복해야 합니다.

**Q. 표시되는 PASS 시각을 그대로 법규 판정에 쓸 수 있습니까?**

하드웨어 지연이 보정되지 않은 값입니다(8장 ②). **0.6초 같은 기준을 판정할 때는 실무상 문제가 없습니다.** 30ms 수준을 다룰 때는 유의미하므로, 캘리브레이션과 onset 보간을 적용해야 합니다.

**Q. 도구가 스스로 소리를 내고 스스로 판정하면 자기 채점 아닙니까?**

시뮬레이터 시험에 한정된 구성입니다. 이때도 **발사와 검출은 분리**되어 있습니다 — 도구가 스피커로 소리를 내지만, 그 소리는 **공기를 거쳐 마이크로 다시 들어와** 독립적으로 판정됩니다. 파일을 직접 비교하는 것이 아닙니다.

실차 시험에서는 경고음이 차량에서 나오고 도구는 관측만 합니다.

**Q. 마이크가 하나면 채널이 하나뿐입니까?**

네. 음향은 1채널입니다. 비전이 2채널(클러스터·기어봉)인 것과 다릅니다. 법규가 요구하는 음향 항목이 "경고음이 났는가" 하나이기 때문입니다.

**Q. 측정 중 마이크가 빠지면 어떻게 됩니까?**

화면에 입력 끊김이 표시됩니다. 이 표시가 필요한 이유는, **끊긴 뒤에는 무음이 조용히 녹음되기** 때문입니다. 그 사실을 모르면 `full.wav`를 보고 "소리가 안 났다"고 잘못 해석할 수 있습니다.
