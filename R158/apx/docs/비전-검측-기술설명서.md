판정 계산은 OpenCV NCC 하나입니다. 다른 지표를 섞지 않습니다. 같은 입력이면 같은 결과가 나와야 하고, 점수가 나온 이유를 식으로 설명할 수 있어야 법규 근거로 쓸 수 있습니다.

## 1. 웹캠 2채널 연결

### 데모에서 보는 것

설정 화면에 **클러스터 설정**과 **기어봉 설정**이 나란히 있습니다. 그룹마다 웹캠 선택 콤보와 실시간 영상 화면이 한 쌍입니다.

### 왜 2채널인가

법규가 재는 것은 두 화면 사이의 관계입니다.

- 기어봉: 운전자가 R단으로 넣었는지 (사건의 시작)
- 클러스터: 후방 경고 팝업이 떴는지 (재려는 결과)

두 화면은 차 안에서 위치가 달라 카메라 한 대로 동시에 담기 어렵습니다. 그래서 카메라를 따로 둡니다.

### 두 채널은 다른 장치여야 합니다

같은 웹캠을 두 채널에 넣는 것은 코드에서 막혀 있습니다.

```java
CameraService other = (this == CLUSTER) ? GEAR : CLUSTER;
if (other.current == cam && other.current.isOpen()) {
    return false;   // 이미 다른 채널이 쓰는 장치
}
```

목록을 다시 읽으면 비어 있는 장치부터 붙습니다. 클러스터가 첫 장치를 가져가면 기어봉은 다음 장치로 갑니다.

현재 지원은 2채널까지입니다. `CameraService`가 두 개로 고정이고 생성자가 바깥에 열려 있지 않아 세 번째 채널은 만들 수 없습니다. Canvas는 여러 개 띄울 수 있지만, 보는 카메라는 둘 중 하나입니다.

### USB를 다시 꽂아도 붙습니다

현장에서 케이블이 빠지는 일이 많습니다. 장치 목록이 바뀌면 도구가 반응합니다.

- 쓰던 카메라가 빠지면: 화면에 "웹캠 연결이 끊어졌습니다"
- 같은 이름의 장치가 다시 꽂히면: 그 장치로 다시 연결

인덱스가 아니라 이름으로 찾는 이유는, USB를 다시 꽂으면 장치 번호가 바뀌는 경우가 많아서입니다.

### 데모 장비 구성

| 채널 | 장치 | 무엇을 보나 |
|---|---|---|
| 기어봉 | OBS 가상 카메라 | 기어봉 이미지 (P / R / N / D) |
| 클러스터 | Logitech C930e | 보조 모니터에 띄운 클러스터 화면 |

가상 카메라를 쓰는 이유는 자극을 프레임 단위로 넣을 수 있어서입니다. 실차 시험에서는 두 채널 모두 실제 웹캠으로 계기판과 기어봉을 각각 찍습니다.

## 2. ROI 지정: 왜 필요한가

### 데모에서 보는 것

웹캠 화면에서 마우스로 드래그하면 사각형이 그려집니다. 그 사각형이 ROI(Region of Interest)이고, 화면에서 여기만 보라는 지정입니다.

### 지정하지 않으면 판정이 틀어집니다

화면 전체를 비교하면 안 됩니다. 촬영 화면에는 판정과 무관한 것이 같이 찍힙니다.

- 클러스터의 속도계 바늘, 시계, 주행거리, 외기온도: 매 순간 바뀝니다
- 계기판 밝기 자동 조절: 주변 조명에 따라 톤이 변합니다
- 프레임 안의 내장재, 스티어링 휠, 반사광

이런 것이 비교에 섞이면 양쪽으로 틀립니다.

- 경고 팝업이 떴는데도 시계 숫자가 달라서 점수가 떨어집니다
- 화면 대부분이 그대로면 팝업이 없어도 점수가 높게 나옵니다

ROI는 판정에 쓸 정보만 남기고 나머지 변화를 막는 장치입니다.

### 어디에 그리는가

| 채널 | ROI 위치 |
|---|---|
| 클러스터 | 후방 경고 팝업이 나타나는 영역만. 속도계, 시계는 제외 |
| 기어봉 | R 글자 또는 R 위치 표시만. 기어 노브 전체는 제외 |

지정하지 않으면 화면 중앙 약 18.75% 크기 박스가 기본값입니다. 실제 시험에서는 직접 지정해야 합니다.

### 드래그하는 순간의 화면이 정답입니다

이 도구는 라이브 캡처를 씁니다. 정답 파일을 따로 두지 않고, ROI를 드래그하는 순간 웹캠 프레임을 정답으로 잡습니다.

- 미리 캡처한 파일이 필요 없습니다
- 정답과 촬영이 같은 카메라, 같은 위치라 각도/조명이 같고, 좌표 보정이 필요 없습니다
- 그래서 해상도만 맞춘 뒤 바로 NCC를 비교합니다

미리 캡처한 PNG를 정답으로 쓰는 방식은 이번 과제에서 쓰지 않기로 했습니다. 파일 정답은 카메라 위치/각도가 캡처 때와 달라지면 ROI가 엉뚱한 곳을 가리키고, 그걸 맞추는 처리가 필요합니다. 라이브 캡처는 그 문제가 생기지 않습니다.

### 데모에서 꼭 지킬 것

경고 팝업이 이미 떠 있는 상태에서 ROI를 그리면 안 됩니다.

그러면 "팝업이 뜬 화면"이 정답이 되어 판정이 뒤집힙니다. 팝업이 없는 정상 화면에서 지정해야 합니다.

기어봉도 같습니다. P단 화면에서 ROI를 그립니다.

### 해상도가 바뀌어도 다시 그릴 필요는 없습니다

ROI는 픽셀 좌표가 아니라 화면 비율(0~1)로 저장됩니다.

```
화면 폭 640px에서 x=200~320을 드래그 → 0.3125 ~ 0.5로 저장
→ 나중에 1280px 카메라로 바꾸면 400~640px로 환산
```

카메라를 바꾸거나 해상도가 달라져도 ROI는 유지됩니다.

### 설정에서 잡은 정답이 측정으로 넘어갑니다

설정 화면에서 잡은 기준 프레임을 측정 시작 때 다시 씁니다. 예전에는 측정 시작 버튼을 누른 순간의 화면을 다시 정답으로 잡아서, 그 사이 화면이 바뀌면 기준이 어긋났습니다. 지금은 설정에서 잡은 것을 먼저 씁니다.

## 3. 판정 원리 (NCC)

### 데모에서 보는 것

ROI 아래에 이런 줄이 실시간으로 바뀝니다.

```
매칭도 (NCC) 96% > 임계치 75%
```

왼쪽이 지금 화면과 정답의 닮은 정도, 오른쪽이 합격 기준선입니다.

### NCC란

NCC(Normalized Cross-Correlation, 정규화 상호상관)는 두 이미지가 얼마나 닮았는지를 -1 ~ +1 한 숫자로 내는 계산입니다.

- `+1`: 완전히 같은 무늬
- `0`: 관계 없음
- `-1`: 명암이 정반대

이 값만으로 PASS / FAIL을 정합니다.

### 정규화가 중요한 이유

이름의 "정규화(Normalized)"가 이 방식을 고른 이유입니다.

NCC는 계산 전에 두 이미지에서 평균 밝기를 빼고 대비로 나눕니다. 그래서 화면 전체가 밝아지거나 어두워져도 점수가 거의 변하지 않습니다.

계기판 밝기 자동 조절, 실내 조명, 카메라 노출이 흔들리는 실차에서 밝기에 덜 흔들리는 점이 필요합니다. 단순 픽셀 차이(SAD/MSE)는 조명이 조금만 바뀌어도 점수가 무너집니다.

### 계산 식

ROI 안 촬영 이미지를 `I`, 정답 이미지를 `T`라 하면:

```
             Σ ( I(x,y) - Ī ) * ( T(x,y) - T̄ )
NCC = ─────────────────────────────────────────────────
       √( Σ ( I(x,y) - Ī )² ) * √( Σ ( T(x,y) - T̄ )² )
```

- `Ī`, `T̄`: 각 이미지의 평균 밝기. 빼므로 밝기 이동에 무관
- 분모의 제곱근: 각 이미지의 대비. 나누므로 대비 변화에 무관

### 실제 구현

OpenCV `matchTemplate`을 `TM_CCOEFF_NORMED`로 씁니다. 위 식과 같습니다.

```java
Mat live = canon.submat(roi[0], roi[1], roi[2], roi[3]);   // ROI만 자름
Imgproc.matchTemplate(liveUse, tmpl, res, Imgproc.TM_CCOEFF_NORMED);
double ncc = res.get(0, 0)[0];                             // 점수 하나
```

ROI 크기와 정답 크기가 같아서 결과는 1x1, 숫자 하나입니다. 정답을 화면 어디서 찾을지가 아니라, 이 자리가 정답과 같은지를 묻습니다. 위치는 ROI로 이미 고정했습니다.

### 지표를 하나로 두는 이유

이미지 유사도 지표는 더 있지만 판정에는 NCC만 씁니다.

여러 지표를 섞으면 어느 지표 때문에 합격/불합격인지 흐려집니다. 법규 인증 근거로 쓰려면 판정 근거가 하나여야 하고, 값이 나온 과정을 식으로 말할 수 있어야 합니다.

### 기준선을 정하는 방법 (데모 시연)

데모 기본값은 75%입니다. 절차는 다음과 같습니다.

1. 정상 화면에서 매칭도를 본다. 높게(90% 이상 권장) 나와야 한다
2. 경고 화면으로 바꿔 매칭도를 본다. 뚜렷이 떨어져야 한다
3. 두 값의 중간쯤에 기준선을 둔다

두 값 차이가 크면 설정이 잘된 것입니다. 차이가 작으면 ROI가 안 바뀌는 영역을 덮고 있으니 ROI를 좁혀야 합니다.

## 4. 시뮬레이션 시작과 자극 발생

### 데모에서 보는 것

시뮬레이션 시작을 누른 뒤, 기어 테스트 화면에서 R 버튼을 누릅니다. 그때 세 가지가 같이 일어납니다.

```
R 버튼 누름
   ├── 기어봉 화면이 P → R 로 전환
   ├── 클러스터 화면이 정상 → 후방 경고 팝업으로 전환   (같은 순간)
   └── 기대 경고음이 스피커로 발사                      (같은 순간)
```

### 왜 세 개를 같이 내는가

실차에서 기어를 R로 넣으면 클러스터 팝업과 경고음이 거의 같이 나옵니다. 시뮬레이터는 그 상황을 재현해야 합니다.

클러스터 팝업을 우리 도구의 판정 결과로 띄우지 않습니다.

"기어봉에서 R을 검출했으니 클러스터 팝업을 띄운다"고 만들면, 자극(화면 전환)이 우리 판정에 묶입니다. 그러면 재려는 시간 차이에 도구 지연이 섞여 30ms 동기 판정이 의미가 없어집니다.

그래서 세 자극은 같은 코드 지점에서 같이 나가고, 도구는 각각 따로 검출합니다. 자극과 측정이 갈라져 있어야 측정값이 의미가 있습니다.

### 판정은 여기서부터 시작합니다

시뮬레이션 시작 때 다음이 고정됩니다.

- 설정 스냅샷: ROI, 기준선, 정답 프레임이 이 시점 값으로 고정됩니다. 측정 중 설정을 바꿔도 판정에 안 들어갑니다
- 공통 시계 0점: 이후 시각은 전부 "측정 시작에서 몇 ms"
- 전 구간 녹화 시작: 두 채널 영상을 통째로 저장합니다

## 5. PASS/FAIL 판정 시점

### 데모에서 보는 것

클러스터 팝업이 뜬 직후 모니터에 이런 줄이 뜨고, 그 뒤로 바뀌지 않습니다.

```
클러스터: PASS @ 1234 ms (자체판단 41.2 = 간격 33.3 + 분석 7.9)
```

### 판정 규칙

```java
boolean hit = ncc >= simThr;          // 점수가 기준선 이상이면 hit
boolean latchNow = hit && !latched;   // 그중 처음 발생한 것만 PASS 시각으로 확정
```

핵심은 래치(latch)입니다. 점수는 매 프레임 오르내리지만, PASS 시각은 기준선을 처음 넘은 그 순간으로 고정하고 이후 바꾸지 않습니다. 나중에 점수가 다시 떨어져도 기록된 시각은 그대로입니다.

법규가 재는 것은 경고가 처음 나타난 시점입니다. 팝업이 깜빡이거나 점수가 기준선 근처에서 흔들려도 시각이 따라 움직이면 안 됩니다.

### 표시 숫자 읽는 법

| 항목 | 의미 |
|---|---|
| PASS @ 1234 ms | 측정 시작을 0으로 한 검출 시각 |
| 간격 33.3 | 카메라 프레임 주기. 30fps면 33.3ms. 사건이 프레임 사이에 나면 다음 프레임까지 기다려야 알 수 있습니다 |
| 분석 7.9 | ROI 잘라내기와 NCC 계산에 든 시간 |
| 자체판단 41.2 | 위 둘의 합. 도구가 만든 지연 |

자체판단을 따로 보여주는 이유는, 측정 결과에서 도구 몫과 차량 몫을 가를 수 있어야 해서입니다.

프레임 주기는 카메라 실측 FPS로 계산하고, 측정값이 없으면 30fps(33.3ms)로 둡니다.

## 6. 최종 판정

### 데모에서 보는 것

시뮬레이션 중지를 누르면 최종 판정이 한 줄로 나옵니다.

### 비전 채널 조건

```
비전 PASS = 클러스터 PASS  AND  기어봉 PASS
```

두 채널이 각각 자기 기준선을 넘어야 비전이 PASS입니다. 한쪽만 넘으면 비전은 아직 FAIL입니다.

### 전체 조건

```
최종 PASS = 음향 PASS  AND  비전 PASS  AND  (채널 간 PASS 시각 최대-최소 ≤ 30ms)
```

마지막이 동기 판정입니다. 채널이 따로 합격해도, 거의 같은 순간에 합격했어야 합니다.

이 30ms가 도구의 계측 정확도인지, 차량 출력의 동시성인지는 고객과 협의 중인 항목입니다. 7장의 정확도 한계와 같이 보면 됩니다.

## 7. 남기는 증거

### 데모에서 보는 것

중지 후 지정한 폴더를 열면 채널별 하위 폴더에 자료가 있습니다. 비전은 `vision/`입니다.

| 파일 | 내용 |
|---|---|
| `evidence_pre_-1f.png` | 판정 직전 프레임 |
| `evidence_decide.png` | 판정이 일어난 프레임 |
| `evidence_post_+1f.png` | 판정 직후 프레임 |
| `full.avi` | 측정 전 구간 녹화 (MJPG) |
| `frames.csv` | 프레임 번호와 시각(ms) 대응표 |
| `matches.csv` | 프레임별 `시각, 합격여부, 점수` 시계열 |

기어봉 채널 증거는 `vision/gear/` 아래에 같은 이름으로 저장됩니다.

### 각각을 남기는 이유

±1 프레임 3장: 판정 프레임 한 장만으로는 직전에는 아니었는지를 보이기 어렵습니다. 세 장이 있으면 바뀐 순간을 눈으로 확인할 수 있습니다.

`frames.csv`: 웹캠 실제 fps는 흔들립니다. 영상 파일의 명목 fps로 시각을 거꾸로 계산하면 틀립니다. 프레임마다 실제 시각을 적어 두면 결과 화면에서 임의 시점을 되짚을 수 있습니다.

`matches.csv`: 결과 화면에서 영상을 되감을 때 각 시점의 합격/불합격 색을 복원하고, 점수가 기준선 근처에서 어떻게 움직였는지 볼 수 있습니다. 기준선을 조정할 근거가 됩니다.

`full.avi`를 MJPG로 두는 이유: 프레임이 각각 저장되는 형식이라, 결과 화면에서 임의 시점으로 되감을 때 해당 프레임이 나옵니다. H.264처럼 압축이 센 형식은 되감기가 부정확하고, Windows 기본 환경에 인코더가 없습니다.

## 8. 정확도 한계

시험 결과를 읽을 때 아래를 같이 봐야 합니다.

### 1) 표시되는 PASS 시각에는 하드웨어 지연이 들어 있습니다

```
표시 시각 = 실제 사건 시각 + 카메라 지연 + 프레임 대기 + 분석 시간
```

카메라 지연(센서 노출 → USB 전송 → 드라이버 버퍼)은 지금 측정하지 않고 보정하지 않습니다. 표시값은 "우리가 알게 된 시각"이고, 사건이 일어난 시각보다 늦습니다.

### 2) 프레임 주기가 정확도의 하한입니다

30fps 카메라는 33.3ms에 한 번만 화면을 봅니다. 사건이 두 프레임 사이 어디에 있었는지는 알 수 없습니다.

| | 오차 |
|---|---|
| 최선 (사건 직후 프레임이 옴) | 거의 0 |
| 최악 (사건 직후 프레임을 놓침) | 33.3ms |
| 평균 | 약 16.7ms |

이 오차는 매 번 달라서 보정으로 없앨 수 없습니다. 줄이려면 프레임 속도를 올리는 수밖에 없습니다. 60fps면 절반(16.7ms)입니다.

### 3) 채널 간 비교에는 두 오차가 같이 실립니다

클러스터와 기어봉을 비교하면 두 카메라 오차가 각각 들어갑니다. 음향과 비교하면 카메라 오차와 마이크 블록 오차가 같이 들어갑니다. 30ms 동기 판정을 볼 때 이 점을 감안해야 합니다.

### 4) 정답 그림의 품질이 판정 품질입니다

정답을 잡을 때의 조명, 각도와 측정 중 조건이 크게 달라지면 점수가 전반적으로 낮아집니다. 그러면 기준선을 낮춰야 하고, 기준선을 낮추면 오검출이 늘어납니다.

설정 단계에서 매칭도가 충분히 높은지 확인하는 일이 시험 신뢰도의 상당 부분을 가릅니다. 3장의 기준선 절차를 데모에서 직접 보여 드립니다.

## 부록 C. 자주 나올 질문

데모와 검토에서 나올 법한 질문입니다. 아직 확정되지 않은 항목은 그렇게 적었습니다.

### 판정 방식

**Q. 카메라로 찍어서 판정하면, 운전자가 실제로 인지한 것과 같다고 볼 수 있습니까?**

같지 않습니다. 이 도구가 재는 것은 화면에 표출된 시점이고, 운전자가 보고 인지하는 시간은 측정 범위 밖입니다.

법규(R158 17.3)가 요구하는 것도 "정보를 운전자에게 제공해야 함"이므로 표출 시점이 판정 대상입니다. 인지, 반응 시간은 별개입니다.

**Q. 팝업이 애니메이션으로 서서히 나타나면 어느 시점을 PASS로 봅니까?**

기준선을 처음 넘는 프레임입니다. 기준선이 "얼마나 나타났을 때를 표출로 볼 것인가"를 정합니다.

기술 문제가 아니라 규격 해석 문제입니다. 팝업이 페이드인되는 차종이면, 기준선을 어디에 둘지 고객과 합의해 문서로 남기는 것이 좋습니다. 같은 기준선을 계속 쓰면 차종 간 비교는 일관됩니다.

**Q. 임계값(기준선)을 사람이 정하면 주관이 들어가지 않습니까?**

들어갑니다. 그래서 정하는 절차를 고정하고 근거를 남깁니다.

- 절차: 정상 화면 매칭도 확인 → 경고 화면 매칭도 확인 → 두 값 중간
- 근거: `matches.csv`에 프레임별 점수가 남아, 나중에 그때 기준선이 타당했는지를 다시 볼 수 있습니다

기준선은 시험 전에 정하고 시험 중에 바꾸지 않는 것이 원칙입니다. 측정 시작 시점 설정이 스냅샷으로 고정되어, 중간에 바꿔도 판정에 반영되지 않습니다.

**Q. AI(딥러닝)를 쓰면 더 정확하지 않습니까?**

각도, 조명 변화에는 더 강할 수 있습니다. 이번 과제에서는 NCC를 씁니다.

이유는 정확도가 아니라 설명 가능성입니다. NCC는 같은 입력에 항상 같은 결과가 나오고(결정론적), 점수가 나온 과정을 식으로 제시할 수 있습니다. 법규 인증 근거로는 이 성질이 정확도보다 앞입니다. 학습 모델은 왜 그 확률이 나왔는지 설명하기 어렵습니다.

### 재현성

**Q. 정답 화면을 시험 때마다 새로 잡으면 재현성이 없는 것 아닙니까?**

정답 프레임은 매번 새로 잡지만, 판정 규칙과 기준선은 고정입니다. 정답을 그 자리에서 잡는 편이 유리합니다. 카메라 위치, 조명이 그날 조건과 같아서 좌표 보정이 필요 없고 점수가 안정적입니다.

다만 지금 부족한 점이 있습니다. 정답 프레임 자체는 증거로 저장되지 않습니다. 판정 직전/판정/직후 3장은 남지만, 무엇과 비교했는지는 파일로 남지 않습니다. 필요하면 정답 프레임도 증거에 넣도록 추가할 수 있습니다.

**Q. 같은 시험을 다시 돌리면 같은 결과가 나옵니까?**

계산은 같은 결과를 냅니다. PASS 시각은 프레임 타이밍 때문에 매번 조금 다릅니다(30fps에서 최대 33ms). 8장 2)의 내용입니다.

**Q. 나중에 결과를 다시 검증할 수 있습니까?**

가능합니다. `full.avi`(전 구간 영상), `frames.csv`(프레임별 실제 시각), `matches.csv`(프레임별 점수)가 남으므로, 결과 화면에서 임의 시점으로 되감아 그때의 점수와 판정을 확인할 수 있습니다.

### 운용 조건

**Q. 차종이 바뀌면 무엇을 다시 해야 합니까?**

ROI 재지정과 정답 재캡처만 하면 됩니다. 코드 변경이나 재빌드는 필요 없습니다. 클러스터 레이아웃이 다르면 ROI 위치가 달라지므로 설정 화면에서 다시 드래그합니다.

**Q. 조명이 바뀌면 결과가 달라집니까?**

밝기 변화에는 강합니다. NCC가 평균 밝기와 대비를 제거하고 비교하기 때문입니다(3장).

위치, 각도 변화에는 약합니다. 카메라가 흔들려 ROI가 다른 곳을 가리키면 점수가 떨어집니다. 시험 중에 카메라를 고정하는 것이 전제입니다.

**Q. 팝업이 아주 짧게 떴다 사라지면 놓칠 수 있습니까?**

놓칠 수 있습니다. 30fps 카메라는 33.3ms에 한 번만 봅니다. 팝업이 그보다 짧게 나오고 프레임 사이에 사라지면 검출되지 않습니다.

법규 대상 경고는 운전자가 인지할 수 있어야 하므로 보통 수백 ms 이상 유지되어, 실무에서는 큰 문제가 되지 않습니다. 짧은 표출을 재야 하면 프레임 속도를 올려야 합니다.

**Q. 두 채널 카메라 성능이 달라도 됩니까?**

동작은 합니다. fps가 다르면 두 채널의 오차 크기가 달라져 채널 간 시각 차이(동기 값)에 편차가 실립니다. 가능하면 같은 기종, 같은 fps를 권장합니다.

**Q. 측정 중 카메라가 빠지면 어떻게 됩니까?**

화면에 연결 끊김이 표시되고, 같은 이름의 장치가 다시 꽂히면 자동으로 다시 연결됩니다. 끊긴 구간에는 판정이 없습니다. 그 구간에 사건이 있었다면 그 시험은 무효로 봐야 합니다.

### 도구 신뢰도

**Q. 도구가 스스로 경고음을 내고 스스로 판정하면 자기 채점이 아닙니까?**

시뮬레이터 시험에 한정된 구성입니다. 사내에서 차량 없이 기능을 확인하기 위한 것이고, 이때도 자극 발사와 검출은 분리되어 있습니다(4장). 도구가 소리를 내지만, 그 소리를 마이크로 다시 받아 따로 판정합니다.

실차 시험에서는 자극이 전부 차량에서 나옵니다. 기어봉, 클러스터, 경고음 모두 차량이 만들고 도구는 관측만 합니다.

**Q. 표시되는 PASS 시각을 그대로 법규 판정에 쓸 수 있습니까?**

하드웨어 지연이 보정되지 않은 값입니다(8장 1). 카메라 지연(센서 노출 → USB 전송 → 드라이버 버퍼)은 지금 측정하지 않습니다.

0.6초처럼 여유가 있는 기준을 판정할 때는 실무상 문제가 없습니다. 30ms 수준을 다룰 때는 이 지연이 의미가 있으므로, 캘리브레이션(도구가 자극을 내고 검출까지 시간을 반복 측정해 상수를 빼는 절차)을 붙이는 것을 검토 중입니다.

**Q. 30ms 동기를 못 맞추면 어떻게 됩니까?**

킥오프 자료 C5에 "한계 시 최대 sync 딜레이에 대한 물리적 설명 및 양사 합의 필요"로 나와 있습니다. 그 설명의 근거가 8장 2), 3)의 프레임 주기 분석입니다.

또한 30ms의 해석(도구의 계측 정확도인지, 차량 출력의 동시성인지)은 아직 확정되지 않았습니다. 별도 질의로 확인 요청 중입니다.

**Q. 3채널 이상은 가능합니까?**

현재 구조에서는 2채널까지입니다(1장). 3채널이 필요하면 채널 관리를 확장해야 하고, 카메라 대수만큼 처리 부하와 동기 오차 항목이 늘어납니다.
